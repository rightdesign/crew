# Command reference

Every command takes an optional `[route]` — a `workspace/project` slug pair.
It may be omitted when the ship has one route (or the command works fleet-wide).
`crew --help` prints the same list.

## Everyday

| Command | What it does |
| --- | --- |
| `crew connect [workspace[/project]]` | Resolve a workspace's ids into `crew.yaml`; on a first run, a setup wizard. A secondary workspace is `<primary>:<slug>`; see [Getting started](/getting-started#a-secondary-workspace). Scriptable with [wizard flags and `--json`](#non-interactive-crew-connect). |
| `crew repos add ROUTE PATH` | Attach a local checkout to a route in `crew.yaml` Creates the Repos row when the tracker has none (`--name`, `--project`, `--no-create`; `--dry-run` previews). |
| `crew repos clone [ROUTE] NAME` | Clone a Repos row's remote (`https://github.com/<owner>/<repo>`, or SSH with `ship.cloneScheme: ssh`) into `<reposBasePath>/<workspace>/NAME` (or `--dir PATH`) and attach it as `crew repos add` would. Refuses a row with no remote or a repo already attached; a failed clone leaves `crew.yaml` untouched. `--dry-run` previews, `--json` emits progress events. |
| `crew repos list ROUTE` | The checkouts a route has, with the Repos row each matches. `--json` prints `{ route, repos: [{ name, remote, repoRowId, attached, dir, exists, origin, matchedRow, hooksSource }] }`: every Repos row the route knows (attached or not), then each configured checkout that matches no row (`repoRowId: null`). `origin` is the checkout's origin URL when it differs from the row's `remote`; `hooksSource` is `repo` (a `.crew.yaml` with hooks), `route` or `none`. The text output is unchanged. |
| `crew repos check [PATH]` | Validate a checkout's `.crew.yaml` (or `.yml`/`.json`) before the repo is attached to any route; needs no `crew.yaml` and no tracker. `PATH` defaults to the current directory; with no spec file it says so and exits 1. A file the loader rejects (unknown key, bad mode, `bump` with `versionFiles`) prints the loader's own message and exits 1. Otherwise it prints the effective settings (`platform`, `release.mode`, `release.versioning`, `branch.*`), the branch and worktree names a sample ticket gets with and without a project tag, and one line per hook with the result of a syntax check by the configured shell (`bash -n` and its siblings, the PowerShell parser; `cmd` has none, so it is reported as not checked). Nothing is executed. A hook that fails its check exits 1. Release-readiness findings (the same wording as `crew doctor`) are warnings and leave the exit status at 0 unless `--strict`. `--route ROUTE` (or `ROUTE NAME`, as the other `repos` subcommands take) resolves the file against that route's ship settings and reports the ship settings the file shadows. `--json` prints `{ file, parsed, effective, readiness, hooks: [{ name, label, syntax }], shadowed, samples, error }`. |
| `crew repos hooks [ROUTE] NAME` | Propose `test`/`build` (and `version`/`bump`) hooks by reading the checkout (`package.json`, `Package.swift`, `pyproject.toml`, `Makefile`; first match wins). `--write route` adds them under the route's entry in `crew.yaml` without overwriting hooks already set; `--write route --replace` overwrites the values it names (keys it does not name stay) and `--json` reports them under `written.replaced`; `--clear route` deletes the route-level `hooks:` map for that repo (comments, other routes and the repo's own `.crew.yaml` are untouched; `--json` reports `cleared.removed`, and `repos list` then shows `hooksSource: none` unless a `.crew.yaml` supplies hooks), and cannot be combined with `--write`, `--suggest` or `--agent`. `--write repo` writes a starter `.crew.yaml` at the checkout root for review and commit, and refuses to overwrite an existing one. `--json` prints the proposal, including `recipes`: named bundles detected from the checkout (a `.github/workflows/` directory offers "Releases run in GitHub Actions", which sets `release.mode: ci_auto` with a `released` hook, and an opt-in "Check CI status before hand-off" recipe that sets `hooks.ci_status`); `--recipes ID,ID` with `--write` applies the ones named (none by default; `release:` settings only land with `--write repo`). `--hook KEY=CMD` (repeatable, with `--write`) overrides the detected value for `test`, `build`, `version`, `bump`, `released` or `ci_status`, or adds one the sniff did not find; the same no-overwrite rules apply (unless `--replace`) and an unknown key is refused with the valid keys named. `--agent` also runs the configured Claude toolchain read-only over the checkout and prints its proposed hooks, the files it read and which values differ from the file sniff; it writes nothing (Ctrl-C cancels), and on failure exits non-zero with a `reason` (`not_signed_in`, `not_installed`, `unsupported_harness`, `timeout`, `cancelled`, `modified_checkout`, `bad_output`, `failed`) while the file sniff stays in the output. |
| `crew reload [--now]` | Make the running `crew daemon` pick up a changed `crew.yaml`. The daemon also notices an edit to `crew.yaml`, a route's `apiKeyFile` or a route's resolved file (which `crew connect` rewrites) on its own. `reload` writes a `reload-requested` marker in the state directory; the daemon then starts no new work, waits for any running agent to end, and relaunches, whether or not its passes are chaining. While it waits it logs a warning every 10 minutes, and `crew status` and `crew doctor` show the pending request and its age. `--now` restarts the unit immediately, interrupting any run in progress. With no daemon unit running it says so and exits 0. `crew doctor` also warns when the config is newer than the daemon's start. |
| `crew doctor [route] [--fix] [--offline] [--json]` | Read-only preflight; prints the periscope settings and checks what hosting needs when a route sets `hostPeriscopes: true`: a missing `ship.previewHost` is a blocker (`preview_host`), one that does not resolve is an attention item (`preview_host_unresolvable`), a repository with no `preview` hook is a note (`preview_hook_missing`) and a workspace without a Periscopes table is a blocker for hosting only (`periscopes_table_missing`; skipped with `--offline`), an issue with more than one `live` Periscopes row is an attention item naming the rows (`periscope_duplicate_live`; skipped with `--offline`); for each checkout it runs `git push --dry-run` against a probe branch (non-interactive) and reports `push auth` ok or the failure with a `gh auth login` / `gh auth setup-git` (HTTPS) or `ssh-add` (SSH) hint, and reports `gh` (required only for PR-based repos), `node` and `docker` (required only with host passengers) with install hints. `--offline` skips the push probes and labels them; `--json` runs only the local checks (no tracker calls) and prints `offline`, `pushAuth` and `tools` plus a `problems` array and a `passed` count (checks that raised nothing); each problem has a `severity` (`blocker`, which also makes the exit status 1; `attention`, an open ship-attention item; or `note`, advice that never changes the exit status), a `kind`, `route`, `repo`, `message`, an optional `remedy`, and for `hook_missing` the `hook` and `command`; `problems` is `[]` when nothing was found; a repo directory missing on disk (or one git cannot check) is reported under that repo and fails the run instead of aborting the report; `--fix` enables clean routes and offers `crew install`. With `ship.relayHost` set and no `--offline`, it also requests `<relay url>/control/status` with the route's key, the way a remote monitor does, and prints `relay control:` with the status and latency or the failure. |
| `crew selftest [route] [--toolchain NAME] [--json]` | Launch each configured toolchain through its adapter as a run would (scheduler `PATH`, scrubbed environment, the dev seat's key as `CREW_API_KEY`, a fresh temp directory) and ask it to read the workspace's name through the tracker MCP tool. Passes when the reply names the workspace; otherwise names the failure (binary not on the scheduler PATH, vendor login missing, MCP tool unavailable, seat key refused, keychain locked, timeout) with its remedy. Reports tokens and cost, writes nothing to the tracker, leaves no worktree or temp directory. Exits 1 if any toolchain fails; `--json` prints one result object per toolchain. `crew doctor` shows the last stored result without re-running it. |
| `crew sample-ticket [route] [--remove] [--dry-run] [--json]` | Create `<dir of the route's first checkout>/crew-sample` if absent (`git init`, a README, a `.crew.yaml` whose test and build hooks always pass, `release.mode: integrate`, `versioning: none`, one initial commit on `main`, and **no remote**: the release phase never pushes for a repo with none), reuse or create its Repos row, attach the checkout to the route, and file one approved, unassigned ticket asking for a small documented function with a test. The description opens with `sample: true`, which is how `--remove` and the app recognize it. Running again reuses the sandbox and files another ticket. `--remove` closes open sample tickets as won't-fix, detaches the route entry, deletes the Repos row and the sandbox directory. `--json` prints one event object per line. |
| `crew install [--replace]` / `crew uninstall [--all]` | Write and load, or unload and remove, this platform's scheduler unit. On Linux with systemd, a non-root run writes user units and enables lingering (`loginctl enable-linger`) so the daemon survives logout and starts at boot; if that is refused, install still succeeds and warns with the command to run. Run as root, it writes system units in `/etc/systemd/system` with `User=` set to `SUDO_USER` (none when there is no such user) instead. On macOS, `install` first clears launchd units left by a crew installed from another path: stale ones are removed, and a unit still running a live other checkout stops the install unless `--replace`. `uninstall --all` removes every `com.tablation.crew*` unit, whichever path it came from. |
| `crew provision --route WS[/PROJECT] [--key K] [--ship-name N] [--forge-host H] [--json] [--dry-run]` | One non-interactive command for a headless host: runs `crew connect --json` for each route, stores a forge token per host, enables the routes, installs the units and starts the daemon. Safe to re-run: each step acts only on a difference, and a run that changed nothing reports `already provisioned`. Inputs are flags or environment: the key from `--key` or `CREW_CONNECT_KEY` (a route's workspace may have its own, `CREW_CONNECT_KEY_<WORKSPACE>`, workspace slug upper-cased with other characters `_` like `CREW_FORGE_TOKEN_<HOST>`; it wins for that workspace's routes and `CREW_CONNECT_KEY` is the fallback), routes from repeated `--route` or `CREW_PROVISION_ROUTES` (comma or space separated), the ship name from `--ship-name` or `CREW_SHIP_NAME`, forge tokens from `CREW_FORGE_TOKEN_<HOST>` (host upper-cased, other characters `_`, e.g. `CREW_FORGE_TOKEN_GITHUB_COM`) or the shared `CREW_FORGE_TOKEN`, for the hosts in repeated `--forge-host` (default `github.com` when a token is set). `--agent-bin`, `--extra-path` and `--base-url` go to `connect`; `--ship-kind KIND` and `--instance-class KEY` go to `connect` too and are written to the Ships row's `kind` and `instance_class` when the workspace has those columns (`connect` alone writes `developer_machine`; a pooled instance passes `pooled_instance`, a reserved managed one `managed_instance`); On a managed ship kind (`managed_instance`, `pooled_instance`) provision also writes `ship.runner: sandbox`, `ship.sandbox.cacheVolume: crew-cache` and `auth: workspace` on every claude toolchain, each only where unset, and `connect` does not require a `claude` on the host; `--runner host` skips that and is logged as an explicit choice (`--runner sandbox` applies it to any ship), and `crew doctor` warns when a managed ship's runner is `host` or a claude toolchain's auth is not `workspace`. `--relay-host HOST` and `--max-concurrent-agents N` are written to `ship.relayHost` and `ship.maxConcurrentAgents` in crew.yaml before the daemon starts; `--choose KEY=VALUE` answers a `choice`. The key and tokens never appear in argv. Exit codes match `connect --json`: 0 done, 1 a step failed, 2 bad input or a problem, 3 a decision is needed (the `choice` event is passed through; re-run with `--choose`). `--json` writes one event per line (`connect` events tagged `phase: connect`, then `forge`, `route_enabled`, `install`, `daemon`, `problem`, `done`); the `done` event's `summary` carries `state` (`provisioned`, `already provisioned` or `dry-run`), `changed`, `routes`, `forges` (`stored`, `rotated` or `unchanged` per host) and `daemon` (`mechanism`, `running`, `lingering`). `--dry-run` runs `connect --dry-run` only. |
| `crew pool-member [--url URL] [--token-stdin]` | For a host with no tenant: registers with the platform, reports `unprovisioned`, long-polls for a lease, provisions itself from the lease payload (`crew provision`, kind `pooled_instance`) and wipes itself (`crew deprovision`) when the lease is released. The URL and pool credential come from `CREW_POOL_URL` and `CREW_POOL_TOKEN` (the flags win; the credential is never an argument). Exits 0 when the platform retires the member, 1 when a provision or wipe failed, 2 when the credential is rejected. Runs as a unit that restarts it; after a restart it resumes from the platform's answer and its own member file. The wire contract and resume table are in [Pooled instances](/pool-member). |
| `crew deprovision [--dry-run] [--json]` | The wipe. Stops the scheduler units, kills every run in flight (recording `run_killed` on the event stream and commenting on each ticket while the seat keys still work), deletes sandbox containers, clears `engaged`, `tunnel_status` and `relay_url` on this ship's Ships rows, revokes the seat keys, removes the workspace credential, Pair/MCP entries and checkouts (forced past local changes), erases every forge token, removes the Docker volumes and repository image layers crew labeled (the base and crew layers stay; anything unlabeled is left alone), empties the state directory and removes crew.yaml last. Then verifies: exits non-zero and lists what remains (`REMAINS:` lines, or `remaining` in `--json`) if crew.yaml, a forge token, a seat key, a labeled volume or image, a sandbox or a scheduler unit still exists. Usable by hand on any host; works with no crew.yaml. `--dry-run` prints the plan and changes nothing. |
| `crew --version [--json]` / `crew version` | Print the version (the `version` in the `package.json` crew resolves for itself, `CREW_HOME` for the compiled binary) alone on one stdout line and exit 0. `--json` prints `{"version", "home", "compiled"}`. Answered before any config is read, so it works with no `crew.yaml` and never touches the tracker. Any other unknown flag still prints usage and exits 2. |
| `crew status [route] [--json]` | Paused/running state, the periscope settings (`periscopes:` line), plus any open ship-level attention items (a parked role, a hook command missing from the scheduler PATH, a stalled release timer) for this ship and, from the Ships table, for others; `--json` for a machine reader (`ship.attention`). The `ships` array in `--json` lists every Ships row with `id`, `kind`, `instanceClass` and `relayUrl` (each `null` when the workspace's Ships table lacks the column, or the tunnel is down) alongside `name`, `lastSeen`, `engaged` and `attention`. A `relay:` line (`ship.relayUrl` in `--json`, null without one) shows the URL this route's tunnel is reachable at; the control API is at `<url>/control/...`. Every live agent run on this ship is listed, one `running:` line each in the text form and a `runs` array in `--json` (`role`, `seat`, `ticket`, `ticketRecordId`, `repo`, `worktree`, `stream`, `pid`, `startedAt`), read from the run sidecars so it holds across daemon restarts; each `crew.seats` entry carries a `running` count. Every live periscope on this ship is listed, one `periscope:` line each in the text form and a `periscopes` array in `--json` (`ticket`, `ticketRecordId`, `periscopeRecordId`, `repo`, `worktree`, `branch`, `url`, `host`, `state`, `isolated`, `startedAt`, `lastActivityAt`, `expiresAt`, `serving`), read from the local record `periscope up` keeps (no tracker call); `serving` is probed on the preview URL's port each time. A seat stays `working` and the ship `engaged` until the last of their runs ends. |
| `crew projects [--route R] [--json]` | The Projects rows each route's connection can read: `id`, `name`, `issuePrefix`, `workMode` and whether it is the route's current `area`. `--json` is `{ routes: [{ route, areaId, projects }] }`; a route whose key fails reports `{ route, areaId, error }`, and the exit code is non-zero only when every route failed. The data source for crew-macos's Project popup. |
| `crew whoami [route] [--json]` | Who each route is signed in as: one `/auth/me` call with the route's key, printing the identity (id, email, name), the key's role in the workspace, the operator Crew row `connect` linked (id, name) and where the credential comes from (`keychain`, `apiKeyFile`, `CREW_API_KEY` or `inline`; never the key itself). `--json` prints an array with one object per route (a single object when a route is named); a route whose key is rejected or unreachable reports `ok: false` with a one-line `error` (a 401/403 names the expired or revoked key), and the exit code is 1 when any route failed. Writes nothing. |
| `crew pause\|resume [route] [ROLE\|release]` | Pause or resume everything, one role, or releases only. `crew pause` stops agents (both one-shot `run` and `crew daemon` claim nothing) and the release timer (merge, deploy, release). `crew pause release` stops only shipping and leaves agents running. Passengers keep running through both. `crew resume` clears only the whole-crew pause, so a release pause stays until `crew resume release`, the same as a role pause. |
| `crew inbox [--member NAME] [--by-route] [--all]` | Your tickets across every workspace, or a colleague's. |

## Running the crew

| Command | What it does |
| --- | --- |
| `crew poll [route]` | Decide a cycle and report it; writes nothing. |
| `crew run [route] [--role R]` | Run the winning role's session (`--role` forces one and disables fall-through; `--max-roles N` sets how many to try). |
| `crew watch [route]` | Live view (`--role`, `--ticket`, `--level warn`, `--tail N`); space pauses, `q` quits. |
| `crew log [route]` | Tail the log. |
| `crew logbook list [route]` | Recent Agent Log entries, filterable by `--role` / `--ticket`. |
| `crew logbook show [route] ID [--prompt]` | One entry; `--prompt` reconstructs and verifies its prompt. |

## Releasing

| Command | What it does |
| --- | --- |
| `crew release [route]` | Merge what QA verified, version it, ship it (`--skip-tests` skips the gate). |
| `crew merge [route]` | Merge verified branches and stop. |
| `crew deploy [route]` | Release now, even with nothing new to merge. |

## Housekeeping

| Command | What it does |
| --- | --- |
| `crew sync [route]` | Fast-forward the checkout and its worktrees from the remote. A base branch that is diverged, ahead of the remote, or cannot fast-forward prints `DO NOT CUT A WORKTREE FROM THIS BASE` and exits 1; `crew status` and `crew doctor` report the same state, and each fetches once per repo to do so. |
| `crew ports [route]` | Which checkout owns which ports, and what is up. |
| `crew sandbox policy --route R --role ROLE [--repo NAME] [--json]` | Print the sandbox policy a run of that role would get (forge, tracker, model route for the toolchain's `auth`, and the repository's declared hosts). Prints; writes nothing. See [the sandbox runner](sandbox-runner.md#the-network-policy). |
| `crew sandbox build [REPO] [--route R] [--json]` / `crew sandbox images [--route R] [--json]` | Sandbox images (see `sandbox:` in the repo spec). `build` forces a rebuild of the image a repository's `.crew.yaml` declares, ignoring the failed-build retry window, and exits 1 if a build failed (the log path is printed and a `sandbox_build_failed` attention item is raised). `images` lists each declaring repository's status (`ok`, `stale`, `missing`, `failed`) and its built tags with ages. The daemon also builds missing or stale images in the background between passes; `crew doctor` prints a `sandbox image:` line per repository. |
| `crew reap [route]` | Kill orphaned servers, drop worktrees for closed tickets and for `verified` ones whose branch is fully on the remote. A worktree whose ticket is a `draft` (a periscope) is never removed and its branch never deleted, clean or not; reap says so. The release-phase sweep follows the same rule. |
| `crew drop [route] NNN` | Remove a merged ticket's worktree and branch. Refuses a `draft` ticket (a periscope's) and points at `crew periscope down`. |
| `crew periscope up [[route] REPO] [--topic TEXT\|--issue NNN] [--isolate] [--serve-mcp] [--host HOST] [--assignee CREW_ROW_ID] [--requested-by ID] [--no-open] [--open] [--dry-run] [--json]` | (alias `start`) Open a periscope: a throwaway running preview of a repository for a viewer. Files a draft ticket `Periscope: <topic>` held by the Pair row (or `--assignee`), cuts its worktree from the remote base, copies `worktrees.copy` files and runs `setup`, then `ports`, `isolate` (only with `--isolate`, recorded as `isolated`) and `handoff`, and finally the repository's `preview` hook with `CREW_PREVIEW_HOST` set to `--host` (default `localhost`). The last stdout line of `preview` is the URL; it is recorded on a `live` Periscopes row that expires after `ship.periscopeIdleMinutes` idle, and a progress comment with the URL and the `handoff` output is posted on the ticket. `--requested-by ID` records who the draft is for as the ticket's reporter (the control API passes it). `--serve-mcp` mints a secret so the daemon serves a [per-periscope MCP endpoint](/periscope#the-periscope-s-own-mcp-endpoint) for the worktree (the control API passes it); `down` revokes it. Prints the ticket tag, the worktree path and the URL; `--json` emits one event per step on stderr and a final `done` object on stdout. `--issue NNN` (mutually exclusive with `--topic`) periscopes a ticket that already exists, such as one parked for planning or held by a person, instead of filing a draft: it refuses (naming the holder, writing nothing) when the ticket is closed, belongs to another repository, is assigned to an agent seat other than this ship's Pair row, is held by another ship, or has a run in flight on this ship. Otherwise it sets the assignee to the Pair row and `held_by_ship_id` to this ship, leaves `status` untouched, records the previous assignee and status in a small file under the ship's state directory (`periscopes/`), and cuts the worktree as `crew worktree` does, from the ticket's pushed branch when there is one. `--json` carries `existing: true` and `priorStatus`. An issue has at most one live periscope: `--issue NNN` first looks for a `live` Periscopes row for the ticket on any ship and, if there is one, refuses before holding or cutting anything, naming its ship, URL and worktree and the `crew periscope down NNN` (on that ship) or `--resume` hint; with `--json` the refusal is also printed on stdout as `{ "refused": "live_periscope_exists", "ship", "url", "worktree" }`. `kept` and `discarded` rows do not count, and `--resume` is exempt. Refuses, before filing anything, when the repository declares no `preview` hook, the workspace has no Periscopes table, or the ship already hosts `ship.maxPeriscopes` live periscopes. A failing `preview` (non-zero exit or no URL) stops what was started, removes the worktree and closes the draft. `--dry-run` reports the refusals and the plan and writes nothing. **From a shell:** with no `REPO`, the working directory names the route and repository: a configured checkout, a subdirectory of one, or a git worktree of one (found through git's common directory); explicit `[route] REPO` arguments win, and outside any configured checkout the command refuses and lists the configured checkouts. `--topic` is optional: at a terminal (stdin and stdout, no `--json`) it is prompted for with the repository name shown, otherwise the draft is titled `Periscope: <repo>, <date>`. At a terminal the URL is then opened (`open` on macOS, `xdg-open` on Linux; `--no-open` suppresses it, `--open` forces it for a script without `--json`) and stdout reads ticket, URL, then worktree path. Piped or with `--json`, nothing is prompted or opened and the output is unchanged. The command never changes the caller's directory; `crew shell-init` provides the function that does. `crew periscope up --resume NNN` restarts the preview of a periscope whose server the idle check stopped: it reruns `ports` (and `isolate` for an isolated periscope) and `preview` in the existing worktree, refreshes the row's URL and expiry and closes the `periscope_idle` item. **Idle expiry:** the daemon checks each live periscope on this ship every pass. A newer file in the worktree (ignoring anything `.gitignore` excludes, so `node_modules` and build output do not count) or a newer `last_activity_at` pushes `expires_at` forward by `ship.periscopeIdleMinutes`. Once `expires_at` passes, whatever listens on the worktree's ports is stopped and a `periscope_idle` attention item (visible in `crew status`, and as `kind` in `--json`) names the ticket, repository and idle time; the row stays `live` and nothing is committed, removed or closed. The item clears when the periscope is ended or activity resumes; the server is not restarted automatically. |
| `crew periscope down [[route] NNN] --keep\|--discard [--allow-empty] [--json]` | (alias `end`) End the live periscope for ticket `NNN` on this ship; exactly one flag is required. `--keep` commits everything in the worktree (refuses when there is nothing to commit unless `--allow-empty`), pushes the branch, appends a `## Prototype` section (changed files and a diff stat, noting the branch may be rewritten) to the ticket, fills `project` and `repo` if unset, clears the assignee, sets the status to `new`, posts a `pushed` event, stops the server, removes the worktree (the branch stays) and marks the row `kept`. `--discard` stops the server, removes the worktree and its local branch, closes the ticket as `closed_obsolete` with a resolution note, marks the row `discarded` and pushes nothing. On a periscope opened with `--issue`, `--keep` still commits, pushes and appends the `## Prototype` section but only clears the assignee and held-by (the status stays as it was), and `--discard` stops the server, removes the worktree, clears the hold and never closes the ticket; the local branch is deleted only when the remote has no copy of it. A periscope already kept or discarded is reported and left alone (exit 0). An isolated periscope's database is left alone. With no `NNN`, the periscope whose worktree holds the working directory is ended; running from inside the worktree being removed is fine, since the command moves to the checkout first. |
| `crew periscope list [route] [--json]` | The `live` periscopes on this ship: ticket tag, repository, worktree, URL, state, minutes since last activity and whether the server is listening. Kept and discarded ones are hidden. |
| `crew shell-init [--shell zsh\|bash\|fish]` | Prints a shell function named `periscope` (the shell defaults to `$SHELL`, else zsh); install it once with `eval "$(crew shell-init)"` in your rc file. A process cannot change its caller's directory, so the bare `crew periscope` never does; the function does: `periscope up ...` runs `crew periscope up --json ...`, relays the progress lines, then changes into the new worktree, prints the URL and path and opens the URL (`--no-open` skips it); `periscope down ...` runs `crew periscope down ...` and on success changes to the repository's checkout; any other subcommand passes straight through. Needs no `crew.yaml`. |
| `crew worktree [route] NNN [dev\|design\|qa]` | Cut, or refresh, this run's worktree for a ticket from the remote branch (fresh from the base when nothing is pushed yet) and print its path on stdout. The route is optional: with none named, a one-route ship uses its route and a multi-route ship takes the route whose tracker has the ticket and whose checkout serves its repo; if none does, or the ticket is on no route, it exits 2 (not 1, which means "left alone" below) naming the ticket's repo and the routes it looked on. It only ever cuts from `<remote>/<branch>` or `<remote>/<base>`, so a stacked branch can only come from a hand-cut worktree. A worktree with uncommitted changes or unpushed commits is left alone: nothing is printed and the exit code is 1. The runner removes a run's worktree when the run ends — after a verified push for dev/design, after the run for QA — unless it is dirty, holds unpushed commits, or the repo's `handoff` hook serves from it; `crew reap` and the release phase then remove a kept one once its ticket is `verified` or closed. |
| `crew disconnect [--reset [--remove-checkouts] [--dry-run] [--json]]` | Bare `disconnect` removes only the Pair/MCP entries `connect` added. `--reset` removes everything `connect` and `install` wrote on this machine, in this order: every scheduler unit for this checkout; the Pair/MCP entries for every route; this ship's seat keys (revoked on the server, then cleared from the keychain); each route's workspace credential in the keychain; with `--remove-checkouts`, the checkouts crew cloned itself; the resolved ids, connect-written key files, sentinels and locks in the state directory (logs and events stay); and `crew.yaml` last, so an interrupted reset can be run again. Server rows (Ships, Crew, Repos) are never deleted. `--remove-checkouts` only touches directories crew recorded when it cloned them, never one attached from elsewhere, and keeps (and names) any checkout with uncommitted changes or linked worktrees. Each removal is printed; `--dry-run` prints the plan and changes nothing; `--json` prints `{dryRun, ok, steps}`. Exits 1 when a seat key could not be revoked or a checkout was kept, since the machine is then not fully clean. Both forms also clear this ship's `relay_url` on each route's Ships row. A seat key minted before key ids were recorded cannot be revoked from here and stays on the server until revoked from its Agents row. |
| `crew ship rename NAME [--json]` | Rename this ship: writes `ship.name` in `crew.yaml` (comments kept) and renames this machine's row on every workspace's Ships table, then records the name each route last saw agree. A route whose key may not edit the table (403) is reported and the local rename still happens; the exit code is 1 then. `--json` prints `{name, previous, configFile, routes: [{route, status}]}`. |
| `crew unassign [route] NNN` | Hand back a session's ticket: clears the assignee so the next cycle picks it up. |

### Periscope settings

See [Periscope](/periscope) for the commands above. The settings live in `crew.yaml`:

| Setting | Default | What it does |
| --- | --- | --- |
| `routes[].hostPeriscopes` | `false` | Lets Passengers open periscopes. Refused at load unless the same route has `hostPassengers: true`; synced onto the Ships row's `host_periscopes` by `crew connect` (skipped on a workspace whose Ships table lacks the column). |
| `ship.previewHost` | — | The host a Passenger reaches this ship by (a LAN name or private-network hostname). Passed to the `preview` hook as `CREW_PREVIEW_HOST` for Passenger-opened periscopes; required once any route hosts periscopes. |
| `ship.maxPeriscopes` | `3` | Periscopes live at once on this ship. A positive integer. |
| `ship.periscopeIdleMinutes` | `120` | Idle time after which a periscope's recorded expiry falls. A positive integer. |
| `ship.secretStore` | `auto` | Where the ship key and per-seat agent keys are kept: `auto` (the desktop secret service where one is reachable; on Linux with no `secret-tool` or no D-Bus session, files under `<stateDir>/keys`, directory `0700` and files `0600`), `os`, or `file`. macOS and Windows resolve `auto` to their own store. A seat whose key cannot be read from the store has its runs refused (a `seat_key_unreadable` attention item and a warning on the event stream) instead of running under the ship key. `crew doctor` prints a `key store:` line naming the store in use and whether it is writable. |
| `ship.env` | — | Environment variables written into every installed unit next to `PATH` (systemd `Environment=`, a launchd `EnvironmentVariables` entry, a crontab prefix), so a proxy or region setting reaches the daemon without editing unit files. A map of name to string; numbers and booleans are stringified. `PATH` cannot be set here (it comes from `ship.extraPath`); a name that is not a valid variable name or a multi-line value is refused at load. Run `crew install` after changing it. |

### Ship name sync

The ship's name lives in two places: `ship.name` in `crew.yaml` and the `name` of this machine's Ships row in each workspace. Each pass of the daemon (and each `crew run`/`poll` cycle), and `crew connect`, compares them against the name that route last saw agree (`shipName` in its resolved file):

- the row changed, `crew.yaml` did not: `crew.yaml` adopts the row's name, with one `ship_renamed` event;
- `crew.yaml` changed (a hand edit), the row did not: the row takes the new name;
- both changed and disagree: the Ships row wins, and a warning event names both values.

The row is matched by `machine_id`. A workspace whose Ships table has no `machine_id` column has nothing to compare, so nothing syncs there; the name in `crew.yaml` stays the name. `crew status --json` reports `ship.name`, `ship.rowName` and `ship.nameDrift` (`none`, `row`, `local` or `both`) without writing anything.

## Non-interactive `crew connect`

A first-run connect needs no terminal when every answer is a flag, and `--json` turns its progress into events a program can read. This is how the Crew app drives setup, and the scriptable path on Linux and CI. The interactive wizard is unchanged for a person at a terminal.

**Wizard answers as flags** (used on a first run, when no `crew.yaml` exists anywhere crew looks):

| Flag | Meaning | Default |
| --- | --- | --- |
| `--ship-name NAME` | How this machine appears on the board | the hostname |
| `--machine-id ID` | Override the stable machine id (hashed) used to find this machine's Ships row before its name; for tests and containers | the hardware id, hashed |
| `--agent-bin PATH` | Absolute path to the agent binary | the `claude` on `PATH`, else in `~/.local/bin`, `~/.claude/local`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.npm-global/bin`, `~/.volta/bin` and `--extra-path` |
| `--extra-path DIRS` | `ship.extraPath` for scheduled runs | derived from where `node`, `pnpm` and (with Host Passengers) `docker` live |
| `--host-passengers` | Host Passengers on this machine | off |
| `--no-wizard` | Never prompt: take every answer from flags and defaults | |

On a terminal the wizard still runs unless `--no-wizard` is given. Off a terminal, any one of the answer flags selects the flag path. An `--agent-bin` that is not executable is a `problem` event and exit 2, never a prompt. A `claude` that cannot be found fails only a real run (after sign-in, naming every directory searched); a `--dry-run` succeeds and its `done` event reports `agentBin: null` with an `agentBinNote`. With a `--key`, the key is written to a 0600 key file (there is no sign-in to put it in the keychain) so `crew.yaml` can name it.

**`--json`** writes one JSON object per line on stdout, each `{event, message, ...data}`; all human text stays on stderr (including the route block). Device authorization needs no terminal under `--json`: the code arrives as a `device_code` event and crew keeps polling.

| Event | Data |
| --- | --- |
| `device_code` | `userCode`, `verificationUri`, `verificationUriComplete`, `expiresIn` (seconds) |
| `signed_in` | `identity` (`id`, `email`, `name` when known), `workspaces`, `session` (`device` for a fresh approval, `keychain` for a resumed one, `key` for a key given on the command line with a workspace named; with no workspace named, a key from `--key` or `CREW_CONNECT_KEY` reports `flag` and a key from a `crew.yaml` route reports `config`, so a client handles those two spellings in addition to `key`). `signed_in` always precedes any `choice` event, including the `workspace` question, so a client knows who is signed in before it is asked anything. With `--dry-run` and no workspace named, a keychain session stored by an earlier run on this host is reused when the server still accepts it, so no `device_code` event is emitted; a missing or rejected one falls back to device approval. With `--dry-run`, a key from `crew.yaml`, no workspace named and exactly one workspace across its routes, that workspace is used without a `workspace` choice: the `signed_in` message says so and `workspace_resolved` follows it. With several workspaces (or none) the `workspace` choice follows `signed_in` as before |
| `workspace_resolved` | `workspaceId`, `slug`, `name`, `role` |
| `project_options` | `options`: each qualifying project (`id`, `name`, `slug`) when several qualify |
| `template_missing` | `canInstall`: no project has the tables a route needs; `true` when the key's role can install the Issues template |
| `template_installed` | `projectSlug` |
| `ship_row` | `id`, `name`, `action` (`created` or `matched`) |
| `operator_row` | `id`, `action` (`matched`, `linked`, `created`, `would-create` for a dry run that would create the row (no `id`), or `previous` for one carried from an earlier connect), `name`, `email` (the row's, else its linked member's; omitted when unknown) |
| `seat` | one per lane: `role`, `id` (empty for `would-create`), `ship_id` (the Ships row the matched row belongs to; empty when none), `action` (`matched`, `claimed`, `created`, or `would-create`: a dry run found no row this machine could claim, so a real run would create one), `key` (the seat-key outcome: `minted`, `already_stored`, `no_agent`, `failed`, `forbidden`, or `none` when none was attempted) |
| `mcp_registered` | `harness`, `bin`, `url`, and for Claude Code `action` (`registered`, `replaced` or `kept`); `message` is the line crew prints |
| `pair_installed` | `harness`; `message` is the line crew prints |
| `config` | `written`, `path` and, when `written` is `false`, `reason`: `exists` (a crew.yaml was already there, so only the route block was printed to stderr for pasting), `appeared while connecting` (a first run lost a race to another writer) or `no-key` (no key file or keychain entry to name). Not emitted by `--dry-run` |
| `capabilities` | reserved for the member capability checklist (ISSUE-2240) |
| `choice` | `key`, `options` (`value`, `label`), `answer`: a decision a terminal would have asked; see below |
| `problem` | `stage` and, for an HTTP failure, `status` and `path`; the run is stopping, or (stage `discover`) the route is written with a gap |
| `done` | `route`, `resolvedPath`, `configPath`, `wroteConfig`, `operator`, `dryRun`, `unresolved` (count) |

**Choices.** Where the wizard would ask, crew emits a `choice` event and exits **3** without writing anything past what is already idempotent. The caller asks, then runs the same command again adding `--choose KEY=VALUE` (repeatable). Re-running is safe: provisioning finds the rows it made.

| Key | Asked when | Values |
| --- | --- | --- |
| `workspace` | no workspace named and the key sees several | a workspace slug |
| `project` | several projects have the tables a route needs | a project slug |
| `install-template` | no project qualifies and the key can install the Issues template | `yes` or `no` |
| `operator` | no Crew row matches the key's identity | a Crew row id, or `new` to create one |
| `status.<value>` | the Issues table has a status the default contract does not know; one event per value | `yes` (resolved/terminal) or `no` |

Exit codes: 0 connected, 2 stopped on a problem, 3 stopped on a `choice`.

## Ship control API

While `crew daemon` runs it serves an HTTP API on a unix socket, `control.sock` in the ship's state directory (mode 0600), for monitoring and control of a ship a client cannot read from disk. If the socket cannot be opened (a path too long for a unix socket, another live process on it) the daemon logs that and runs without it.

Every request, including one to an unknown path, needs `Authorization: Bearer <key>`. A key is accepted when it is one of the ship's own tracker keys, or when Tablation accepts it for a workspace the ship serves (`/api/auth/me?workspaceId=`, the check the relay makes), reusing a verdict for 60 seconds. A key Tablation rejects gets 401, a key that belongs to no served workspace gets 403, and a tracker that cannot be reached gets 503 (nothing is accepted without a check).

| Request | Answer |
| --- | --- |
| `GET /status` | The `crew status --json` document, plus `daemon` (`alive`, `pid`, `startedAt`, `uptimeSeconds`) and `pause` (`crew`, `release`, `roles`). |
| `GET /events?after=CURSOR&tail=N&wait=SECONDS` | `{ lines, cursor, reset }`: the event-log lines written since `after`. With no `after`, the last `tail` lines (default 100). `wait` (up to 30) holds the request until a line is written. A rotated log is read to its end before the live file; `reset` is true when the cursor could not be honored and the read restarted. |
| `GET /streams` | `{ streams }`, one per live run: `run`, `pid`, `ticket`, `role`, `model`, `startedAt`, `deadline` (always `null`: no run limit is enforced). |
| `GET /streams/RUN?after=CURSOR&tail=N&wait=SECONDS` | The same tail for one run's stream. |
| `POST /pause`, `POST /resume` | Body `{ "role": "dev" \| "design" \| "qa" }`, or `{}` for the whole crew. The same marker files `crew pause` writes, so the next daemon pass and `crew status` see it. |
| `POST /release/pause`, `POST /release/resume` | Pause or resume releases only. |
| `POST /scheduler/start`, `stop`, `restart` | 202 once requested; runs the same service-manager commands as `crew daemon start\|stop\|restart` from a detached shell, since stopping ends the daemon. 409 on a host with no service manager for the daemon. |
| `GET /doctor` | The `crew doctor --json` report. Read-only: never `--fix`, and the offline form. |
| `POST /periscopes` | Body `{ "route"?, "repo", "topic", "isolate"?, "requestedBy"? }`. Opens a periscope by running `crew periscope up` with `--host ship.previewHost`; `requestedBy` (a workspace membership id the chat passes) becomes the draft ticket's reporter while the Pair row stays the assignee. Answers the `up --json` result (ticket tag, URL, worktree, branch). `route` may be left out when exactly one route hosts periscopes. 409 and nothing filed once `ship.maxPeriscopes` live periscopes exist or when `ship.previewHost` is unset. |
| `POST /periscopes/TICKET/down` | Body `{ "outcome": "keep" \| "discard", "allowEmpty"?, "route"? }`. Runs `crew periscope down` and answers its result: `keep` leaves the ticket at `new` and the row `kept`; `discard` closes it `closed_obsolete` and marks the row `discarded`. 404 when the ship has no such periscope. |
| `GET /periscopes?route=ROUTE` | `{ periscopes }`: the `crew periscope list --json` rows for the hosting routes (all of them, or the one named), each with its `route`. |

The three `/periscopes` operations exist only while a route sets `hostPeriscopes: true`; otherwise they answer 404 as if absent, and that flag is the authorization. Beyond the bearer check above, the caller's key must belong to the workspace of the route it names (403 otherwise; a listing across routes leaves out the ones the key is not in). `up` and `down` print one progress event per step; send `Accept: application/x-ndjson` (or `?stream=1`) to receive them as NDJSON lines followed by the final `done` object, or `{ "event": "error", "status", "message" }` on failure. Without it the reply is the final object alone. A refusal found before anything starts (flag off, bad body, cap reached, wrong workspace) is always an ordinary 4xx.

A cursor is opaque; send back the one the last answer returned. Only whole lines are returned. Setup, connect, key minting and provisioning are not exposed, and no endpoint accepts or returns a key.

## Minimum crew version

A project can set a minimum crew version. A crew below it claims no ticket, keeps its heartbeat, and raises a `crew_outdated` attention item (shown by `crew status`) naming both versions; it clears itself once crew is updated. Tracker writes from an older crew are refused with HTTP 426. The Crew app updates its built-in crew; on the CLI, update with `npm install -g @tablation/crew` or the newest binary release. See [If something's stuck](/getting-started#if-something-s-stuck).

## Forge credentials

A ship can hold its own git token instead of relying on whatever auth the host's git has. Declare it per host under `ship.forges` in `crew.yaml`:

```yaml
ship:
  forges:
    github.com:
      # username: x-access-token   # the default; GitHub accepts any non-empty name for a PAT
      token:
        source: file              # file | keychain | env
        # path: ~/secrets/gh.token   (file; default <stateDir>/forges/<host>.token)
        # service: crew-forge        (keychain)
        # var: GH_PAT                (env)
```

- A **file** source is created with mode 0600 and refused when group- or world-readable. **keychain** uses the macOS Keychain or `secret-tool` on Linux. **env** reads a variable and cannot be written by crew.
- `crew forge set <host>` configures the entry (first time: `--source file|keychain|env`, plus `--var` for `env`) and stores the token from `--token T`, `--token-stdin` or `CREW_FORGE_TOKEN`. `crew forge rotate <host>` replaces it. `crew forge` lists hosts and whether a token is present.
- Which forge a repository lives on comes from the Repos row's `forge_host` column (blank means `github.com`; `crew connect` copies it into the route's resolved block). Clone URLs for `crew repos clone`, the lazy clone before a ticket, and the Host Passengers checkout are built for that host: `https://<host>/<remote>.git` or `git@<host>:<remote>.git`. A host with a token in `ship.forges` is always cloned over HTTPS; otherwise the checkout's origin scheme, then `ship.cloneScheme`, decides. A GitLab host (`gitlab.com`, or any host name containing `gitlab`, including self-hosted) has `oauth2` as its default credential username; GitHub keeps `x-access-token`. `crew doctor` prefixes a push failure with the host.
- Crew's own git commands and every agent run get `crew credential` as git's credential helper through `GIT_CONFIG_COUNT` environment. No `.gitconfig`, `.git-credentials`, remote URL or argv carries the token. Agent runs also get it as `GH_TOKEN`, `GITHUB_TOKEN` and `CREW_FORGE_TOKEN`.
- With a token for `github.com`, clones use HTTPS regardless of `ship.cloneScheme` or the checkout's `origin`.
- `crew doctor` runs its push probe through the helper. A missing token, a token that can fetch but not push (read-only), and a refused token are each reported naming the host.
